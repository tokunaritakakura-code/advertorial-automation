# プロンプトと文書の書き方 — 質が出る形（全スキル・全依頼で使う）

`skill-format.md` は**並び順**の規範。こちらは**中身の書き方**の規範。両方通す。

**適当に書くと、読む側（人でもエージェントでも）が必ず間違える。**
2026-08-24 の実測: 独立監査4体に同じ対象を投げて、4体とも使える指摘を返した。
一方、同じ日に自分が書いた「直した／直した／直した」の羅列は、何が壊れていたのかが消えていて読めなかった。
**差は書き方だけ。** 以下はその差を規則にしたもの。

---

## 1. エージェントに投げるプロンプト（監査・調査・生成すべて）

### 効いた形（4体とも高い解像度で返った）

| 要素 | 書き方 | 効く理由 |
|---|---|---|
| **役割を先に固定** | 「あなたは批判的な監査人です。壊しに行くのが仕事です」 | 立場が無いと平均的な要約が返る |
| **結論を1行目に強制** | 「判定: 〜 のどれか、1行で」 | 読む側が最初の1行で判断できる |
| **出力の見出しを先に列挙** | 「出力: 判定／捉えている点／捉え損ねている点／失敗例3つ以上／直すべきこと（優先順）」 | 形を決めないと切り口が毎回変わって比較できない |
| **禁止を明示** | 「褒めるな」「一般論を書くな」「推測で書くな」「使えない指摘を書くな」 | 否定形は守られにくいが、**この4つだけは書くと明確に効いた** |
| **検証手段を指定** | 「必ず実行して確かめてから書け」 | 指定しないと読んだだけで断定する |
| **引用を強制** | 「ファイル名と該当箇所を引用して具体的に」 | 引用を要求すると、実在しない主張が減る |
| **反証を要求** | 「この通りにやって失敗するケースを3つ以上構成しろ」 | 賛成の材料だけ集めるのを止める |
| **自分の結論を渡さない** | 監査対象のパスだけ渡す。自分の判定は1行も書かない | 渡すと必ずそれをなぞって返ってくる |
| **観点を分けて並列** | 本質／再現性／抜け漏れ／総合 を別の相手に | 1体に全部やらせると全部が浅くなる |

### 書くな

- 「よろしくお願いします」「丁寧に」「しっかり」→ 情報が0。文字数だけ増える
- 「良い感じにして」→ 基準が無い。必ず平均的な物が返る
- 自分の仮説を先に書いて「これで合ってますか」→ 同意しか返らない

## 2. 直した記録の書き方（一番間違えやすい）

**「直した」だけ書くな。壊れていた状態を書け。** 直った状態だけ残すと、
なぜその形なのかが消え、次の人（次の自分）が同じ所を「無駄だから」と戻す。

### 形（2列で並べる。表にする）

```
| # | 何が壊れていたか（現象＋なぜ致命的か） | どう直したか |
```

- **現象を数字と固有名で書く。** 「リンクが壊れていた」ではなく
  「絵ノート3本が全部 `![[00s.jpg]]` で同じ画像を指していた。関門Aの唯一の出力物が信用できなかった」
- **直していないものを同じファイルに、重い順で残す。** 消すと「全部直った」に見える
- **落ちた実験を消さない。** 間違えた記録が次の関門になる

---

## 3. 主張の書き方

| 規則 | 理由 |
|---|---|
| **母数を主張の横に書く**（n=1 なら n=1 と書く） | 書かないと、1本から出した観測が法則として読まれる |
| **出どころ記号を値に付ける**（実測 / 引用 / 自分の判断） | 判断と実測が混ざった瞬間、全部が信用できなくなる |
| **取れなかったものを0件と書かない** | 「取得失敗」と「本当に0件」は別物。混ぜると次の判断が壊れる |
| **借り物の数字を自作の物に付けない** | 実測の事故: 検証済み手法の的中率75%を、未検証の自作52項目の根拠欄に書いていた |
| **IDや番号を書いたら、出どころのリンクを一緒に貼る** | 番号だけでは後から辿れない。控えを1ファイルに集めて、成果物からそこを指す |
| **矛盾を見つけたら、片方を消すか「未解決」と書く** | 両方生かすと、次に読む人がどちらを読むかで正反対の行動を取る |
| **撤回した結論に「撤回済み・引かない」と書いて残す** | 消すと、また同じ推論をやり直す |

## 4. スキルを作る／直す時に必ずやること

1. `skill-format.md`（並び順）と、このファイル（中身）を**両方**通す
2. **関門を冒頭に置く。** 毎回やることを「指示待ち」にしない。
   実測の事故: 「1秒刻みで絵を見る」を手順に書かなかったので、指示されるまでやらなかった
3. 関門には**なぜそれをやるかの証拠を1行**添える。理由が無い規則は破られる
4. **決定的な処理はコードに落とす。** 文章の規則は破れるが、コードの規則は破れない
5. 書き終わったら `check-nolost.py` と `check-drift.py` を**両方向**かける
6. **他人（文脈ゼロの独立エージェント）に監査させる。** 自分で作った物の穴は自分では見えない

---

## 5. 出力の形 — 読む相手が2人いる

**同じ内容を2回書かない。ターミナルは結論、ファイルは根拠。ターミナルからファイルを指す。**

| | 本人（ターミナル） | 自分と次のエージェント（ファイル） |
|---|---|---|
| 求めている物 | **結論と、自分が次にやること** | **再現できる根拠** |
| 長さ | 短い。画面1〜2枚 | 長くてよい |
| 過程 | **書かない** | 全部書く |
| コードの説明 | **書かない** | スクリプトに書く |
| 数字 | 効いた物だけ | 全部。母数と出どころ記号つき |
| 落ちた実験 | 1行 | 経緯ごと残す |

### ターミナル側の形（固定）

```
1. 判定・結論を1行           ← 最初の1行で読み終われる状態にする
2. 効いた事実を2〜4個         ← 各1〜3行。主語を太字。数字と固有名を必ず入れる
3. まだ駄目な所（あれば）      ← 重い順。無ければ書かない
4. 保存先と、次にやること1行   ← 本人の行動で閉じる
```

**書くな**: 前置き／過程の実況／「〜しました」の羅列／コードの説明／褒め／
判断を聞く質問（自分で決めて、決めた事を書く）。

### ファイル側の形（固定）

`skill-format.md` の並び順（関門→参考→手順）＋ 本ファイル 1〜4節。加えて:
- 値には出どころ記号（実測 `T/F/A/M` ／ 判断 `J`）
- 主張の横に母数（n=1 なら n=1）
- 未着手を同じファイルに重い順で残す

### 対応（本人が読む1行 ↔ ファイルのどこ）

ターミナルの各行は、**必ずファイルの実物を指す**。指せない行は書かない。

| ターミナルの行 | 指すファイル |
|---|---|
| 判定 | `_監査-*.md` の冒頭 |
| 効いた事実 | その数字を出した実物（`シーン/*.md`・`絵/*.md`・`raw/*.json`） |
| まだ駄目な所 | `_監査-*.md` の「まだ直していない」 |
| 次にやること | 手順の Step 番号 |
