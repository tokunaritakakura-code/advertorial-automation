# brain（脳を整理する）

`/study` が集めた教材を、**制作で読まれる形**に変える。

```
Obsidian Vault/ec/wiki/ads-brain/
  _map.md         入口。全playbookが1行ずつ。制作は必ずここから入る
  _log.md         取り込み台帳（重複防止）
  _conflicts.md   教材が食い違った所と、その裁定
  playbooks/      制作の入力になるのはここだけ
  sources/        教材1本＝1枚（証拠。制作では読まない）
  raw/            文字起こし。Claudeは読まない。slice.py と grep だけが触る
```

**なぜこの形か**

- 制作のたびに教材を読み直すと、毎回1万トークン以上を溶かす。playbook は1本2000〜8000字に固定する
- 教材は矛盾する。矛盾を playbook に持ち込むと制作が止まる。裁定を `_conflicts.md` に外出しする
- 出典IDを残すので、playbook の1行から元の教材まで戻れる。**戻れない知識は信用しない**

**このファイルの並び順は意図的。** 冒頭＝外せない関門、中盤＝参考（引くもの）、末尾＝実行手順。

# 1. 関門 — ここを通らないものは成果物にしない

## やってはいけないこと

- source の文章を playbook にコピーする（playbook は圧縮した命令であって、要約ではない）
- 出典IDを付けずに主張を書く（後で誰も検証できない）
- 1回の統合で playbook を5本以上いじる（どこで壊れたか分からなくなる）
- **裁定していない論点を playbook に書く。** 迷ったら書かずに保留する
- **1回の広告テストで playbook 全体を「実証あり」にする**

## check が0になるまでが仕事

```bash
python3 ~/.claude/skills/brain/scripts/brain.py check
```

出るのは8種類。地図落ち / 地図の幽霊 / 出典切れ / 主張ID違い / 未統合 / 台帳落ち / 確度なし / 太りすぎ。
問題があると終了コード3を返す。**0にならないうちは報告しない。**

裁定できない教材を無理に統合しない。**台帳の状態を `保留` にすれば `check` の未統合リストから外れる**
（保留のまま放置していい。裁定材料が増えたら戻ってくる）。

## playbook の型（欄を減らさない）

**この型も研究から決めている**（`references/learning-science.md` 層3）。効くのは4つ。

- **例が1つだと転移しない。** 2つ以上の例から共通の型を言葉にして初めて、別の商品に使える
  （Gick & Holyoak 1983）→ **「共通の型」欄を必須にし、出典が1本のルールは「仮説」と表示する**
- **手順にサブゴールの見出しを付けると、初見の問題を解ける率が上がる**（Catrambone 1998）
  → 手順を番号だけで並べない
- **抽象ルールだけでは使えない。お手本が要る**（Renkl et al. 1998）→「お手本」欄を必須にする
- 「〜を検討する」と書かず、完全な手順を与える（Kirschner, Sweller & Clark 2006）

```markdown
---
topic: <トピック名>
updated: YYYY-MM-DD
confidence: 実証あり | 教材のみ | 未検証
sources: [<slug>, <slug>]
---

# <トピック名>

## いつ読む
（どの作業の、どの瞬間に開くか。1〜2行）

## 共通の型
（複数の教材・事例に共通していた構造を、商品名を出さずに1段落で書く。
 ここが空だと、この playbook は別の商品に使えない。
 出典が1本しか無い場合は「まだ1例のみ。型として書けない」と正直に書く）

## 手順

### サブゴール1: <この段階で何を確定させるか>
1. <命令形。判断が要る所は数字で固定する>
2. ...

### サブゴール2: <...>
3. ...

## 判断基準
- <数字で書く。「多い」ではなく「9本以上」>

## お手本
（実際にこの型で書かれた現物を1つ。無ければ「まだ無い」と書く。作り話を置かない）

## よくある失敗
- <やりがちなこと → 何が起きるか>

## 根拠と確度

| ルール | 出典 | 独立した裏付け | 状態 |
|---|---|---|---|
| <手順の何番か> | <slug>#c07 | 1本 | 仮説 |
| <...> | <slug>#c02, <別slug>#c05 | 2本 | 定説 |

## まだ埋まっていない穴
- <この playbook が答えられないこと>
```

**縛り**

- 8000字を超えたら割る。長い playbook は制作で読まれず、無いのと同じになる
- 手順の行に形容詞だけの表現を残さない（「強いフックを書く」は禁止。
  「フックは3秒以内に痛みを名指しする」にする）
- 出典は `（<source-slug>#c07）` の形で書く。全角括弧でよい。この形でないと検査に引っかからない
- `confidence` を必ず入れる

## ルールの状態の決め方

Gick & Holyoak 1983 の「2例で型ができる」に合わせている。

| 状態 | 条件 |
|---|---|
| 仮説 | 出典1本。使ってよいが、外れても驚かない |
| 定説 | 独立した出典2本以上が同じことを言っている |
| 実証 | 上に加えて、自分の広告の結果で同じ向きが2回以上出た |

**「独立」は機械が判定できない。ここは人が見る。**
同じ元ネタを引き写した2記事、同じ人が書いた2教材、片方がもう片方を引用しているもの、
これらは2本に数えない。数えると「2本あるから定説」が形だけになり、この脳の一番大事な仕切りが機能しなくなる。
疑わしい時は、片方の教材の参考文献と発信者を確認してから数える。

**playbook 全体を `実証あり` にできるのは、その playbook の手順すべてが自分の広告の結果で
裏取りできている時だけ。** 1回の9本テストで裏が取れるのは普通1〜2行なので、
その場合は行ごとに `（実証: <広告ファイル名>）` を付け、playbook 全体は `教材のみ` のままにする。

## 食い違いの裁定基準（上から順）

1. 日本の市場・法規で使えるか（薬機法で言えないことは、どれだけ効いても採らない）
2. 実際に回っている広告で見えるか（`/gethookd` の実測と一致するか）
3. 教材の作者が実際にそれで売っているか（教えるのが本業の人より、売っている人を採る）
4. 新しい方

## 閉本テストを通す（飛ばさない）

**要約で終わらせない。** 学習研究で一番効くのは練習テストで、要約は最低クラスに置かれている
（Dunlosky et al. 2013）。

`coverage` が「宙に浮いている」と言う主張が1つでもあるうちは、次に進まない。
答えられなかった主張は2択で処理する。**playbook に足す**か、
**意図的に捨てるなら source の「採らなかった主張」に理由付きで移す**。

**「答えられた」と自分で言わない。** 採点は機械（文字3-gramの重なり）で出す。

## 報告に必ず入れるもの

- 統合した教材の数と、増えた/更新された playbook 名
- 裁定した食い違いと、採った方の理由
- **まだ `未検証` の playbook 一覧**（これが「まだ信じるな」のリスト）
- check の残り件数（0であること）
- **判断グラフ側を作り直した playbook 名と、wakeru check の結果**

# 3. 実行手順

## Step 1. 何が溜まっているか見る

```bash
python3 ~/.claude/skills/brain/scripts/brain.py check
```

## Step 2. 未統合の教材を playbook に落とす

未統合の source を1本ずつ開き、主張リストを見て、行き先の playbook を決める。

| 状況 | どうする |
|---|---|
| 既存の playbook に**同じことが書いてある** | 出典IDを追記するだけ。文は増やさない |
| 既存と**言っていることが違う** | Step 3 の裁定に回す。playbook にはまだ入れない |
| **どの playbook にも入らない** | 新しい playbook を作る（トピックが1つ増える時だけ） |

## Step 3. 食い違いを裁定する

`_conflicts.md` に1行足す。基準は冒頭の関門「食い違いの裁定基準」に従う。

| 論点 | A（出典） | B（出典） | 採用 | 理由 | 日付 |

## Step 4. playbook を書く

`playbooks/<topic>.md`。型は冒頭の関門に従う。

## Step 4.5. 閉本テストを通す

```bash
# 1. 問いを出す（主張の中身は1文字も出ない）
python3 ~/.claude/skills/brain/scripts/selftest.py questions <sources/xxx.md>
```

**ここから source を開かない。playbook だけを見て、この教材から来た指示を全部書き出す。**
書いたものをファイルに保存してから、

```bash
# 2. 機械採点（自己申告にしない）
python3 ~/.claude/skills/brain/scripts/selftest.py answers <sources/xxx.md> --recall <答えのファイル>
# 3. 機械的な網羅チェック
python3 ~/.claude/skills/brain/scripts/selftest.py coverage <sources/xxx.md> <playbooks/yyy.md>
```

一致が低い主張は、playbook からその情報が落ちている。

## Step 5. 地図を更新する

`_map.md` の表に1行。**書くのは「いつ読むか」であって、要約ではない。**

| playbook | いつ読む | 確度 | 更新 |
|---|---|---|---|
| advertorial | アドバトリアル型のLPを書く前 | 教材のみ | 2026-08-14 |

地図は100行を超えさせない。超えたらトピックを束ねる。

## Step 6. もう一度 check

```bash
python3 ~/.claude/skills/brain/scripts/brain.py check
```

終了コード0になったら完了。

## Step 7. 触った playbook を判断グラフ側にも反映する（飛ばさない）

**playbook を直しただけでは、制作中に開く側（`判断/`）は古いまま。**
制作の入口は `_入口.canvas` なので、ここを通していない更新は**存在しないのと同じ**になる。

```bash
S=~/.claude/skills/wakeru/scripts/wakeru.py
B=~/Documents/Obsidian\ Vault/ec/wiki/ads-brain

# 触った playbook の spec を直してから
python3 $S build "$B/判断/_spec/<topic>.json" --base "$B"
python3 $S check "$B"     # 終了コード0になるまで
```

- 直すのは **`判断/_spec/<topic>.json`**。canvas を手で編集しても次の build で消える
- **分岐（状況で変わる）／固定（毎回同じ）／誤差因子（決められない）** の3つに仕分けてから書く。
  やり方は `/wakeru`
- playbook を新設したら `判断/_spec/_index.json` にも足して `index` を回す
- **本文は消さない。** playbook は辞書として残す

</procedure>
